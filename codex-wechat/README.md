# 微信 + Codex 单机版（开发中）

微信电脑独立运行：微信数据库采集 → 本地持久队列 → Codex CLI + Skill → 微信 UI 发送。无需旧主服务、Docker、服务器连接、桥接令牌、fastembed、ONNX 或向量语义模型。

本版本已实现可测试的第一条链路。真实微信采集与 UI 发送沿用原项目的驱动；新调度器、Codex 连接和 Skill 的组合尚需在实际微信账号上联调。开发验证只调用模拟 Codex 和模拟发送器，没有调用真实模型或发送微信。

## 安装与启动

1. Windows 电脑安装 Python 3.12，在项目根目录运行 `install_python312.cmd`，创建或补齐统一的 `.venv-analysis`，通过根目录 `requirements.txt` 一次安装全部工具依赖。本目录的 `安装单机版.cmd` 也调用同一个安装入口；旧的 codex-wechat/.venv 不再使用，不自动删除。
2. 安装 Codex CLI，运行 `codex login`，先在终端验证 Codex 可用。若可执行程序不在 PATH，在配置 `codex_command` 中填写路径。支持原生 `codex.exe`，也支持标准 npm 安装目录的 `codex.cmd`（内部用 Node 入口启动，不将聊天内容拼入 shell）。
3. 编辑 `wechat.codex.json`；没有该文件时从 `wechat.codex.example.json` 复制。默认开启Codex回复和发送，数据库目录为 `D:/xwechat_files`，数据库账号为 ``。会话可为空，启动后保持待配置模式，不读取微信数据库、不调用Codex或发送消息；添加会话并保存后安全重启监听。已有配置的明确设置不会被新默认值覆盖。
4. 先执行检查：`..\.venv-analysis\Scripts\python.exe -m wechat_local --check`。此操作只读检查 Python 环境、全部运行依赖、Codex 启动路径、数据库账号目录及源文件读权限、状态目录写权限和 UIA 配置格式；不提取密钥、不创建缓存、不操作微信、不调用 Codex、不发送。`errors` 非空时返回退出码 1，需先处理；`warnings` 是需留意的事项。`ready_for_capture_attempt=true` 仅表示可以尝试采集，**不代表真实链路已验证**。数据库解密、登录账号、聊天名单、Codex 登录与模型可用性、UIA 版本兼容和发送能力列在 `unverified` 中，仍需分阶段联调。缺少基础依赖时也会输出诊断 JSON。
5. 运行 `启动单机监听.cmd`。`codex_enabled=false` 时只采集记录，空闲不会唤醒 Codex。把 `codex_enabled` 改成 `true`、聊天的 `reply` 设为 `true` 后，符合条件的新文字消息才会生成回复；`allow_send=false` 时保存为预览，不发送。修改配置后重启监听。
6. `allow_send` 首次默认开启；需要预览时可以显式关闭，确认后再开启并重启。已存的预览不会自动补发。空会话 `--check` 显示 `idle_mode=true`，不把缺少聊天作为错误；`ready_for_capture_attempt=false` 表示没有配置采集目标。

示例聊天配置（ID 是本地稳定标识，username 是微信原生账号或群 ID；不是昵称）：

```json
{
  "id": "my_group",
  "name": "群的准确显示名称",
  "kind": "group",
  "username": "123456@chatroom",
  "reply": true,
  "persona": "用简洁、友好的中文回复。"
}
```

私聊使用 `kind: "private"`。群聊仅在新消息 @当前登录账号时回复，群内 `/` 指令继续关闭。首次采集得到的历史消息、自己发送的消息、图片和语音不会触发回复。原始内容仍可本地归档。私聊与群聊只处理名单内会话。

不要同时运行旧收发端和新监听器操作同一个微信账号。每个独立缓存有进程锁，但不同目录的两个程序不能相互阻止。

## 本地搜索与 Skill

Skill 在 [.agents/skills/wechat-chat/SKILL.md](.agents/skills/wechat-chat/SKILL.md)。监听器为当前聊天建立独立工作目录，并复制 Skill 和搜索脚本。Codex 使用只读执行模式，接收有限的近期消息，需要回忆时自主调用参数化 SQL 搜索、日期筛选、分页和命中上下文读取。聊天快照增量更新，避免每次重写整份存档。

当前搜索是关键词子串匹配，可直接搜索中文，没有向量模型；数据量很大时仍会扫描文本，尚未加入全文索引。Codex 可换关键词多轮查找，但这不等同于向量语义检索。

附件第一阶段只支持手动放入当前聊天工作目录 `files/` 的 UTF-8 文本（txt、md、csv、json、log），单文件最多 2 MiB，搜索与读取有分页。尚未自动从微信下载附件，也未实现 PDF、Office、OCR 或语音转写。脚本会拒绝目录穿越和指向外部的文件路径。

## 同步工具下载文件

文件发送采用“模型判断意愿、监听程序执行”的流程。用户可以先自然地询问某个文件的位置，再说“把刚才那份发给我”。提示词要求模型确认当前用户明确的发送意愿和所选文件；只查找、询问能否发送、暂不发送或意愿不清楚时不能提出发送操作，必要时先向用户确认，不限定命令格式。

模型通过独立的 `file_action` 字段提出操作，只能使用当前授权台账返回的文件 ID。监听程序核对当前聊天授权、文件版本及 SHA256，复制出待发送快照后交给微信发送器。查找结果按聊天与提问人分别保存，15 分钟内供模型理解后续指代；不会把其他人的查找结果作为当前提问人的选择。单次最多直接发送三份文件，超过三份自动打包为 ZIP；一个 ZIP 超限时按完整文件边界拆成多个独立 ZIP，每个均不超过单文件上传上限；用户明确要求压缩包时也会打包。同名文件放入 ZIP 中的独立编号目录，避免覆盖。目标仅限当前聊天；微信上传通道默认单文件上限 900 MiB（943,718,400 字节，约 944 MB），可通过 `file_send_max_mib` 调低（最大 900 MiB）。该值低于 1GB 参考值，并留有余量；目前未能核验个人微信聊天的统一官方上限声明，因此这是程序的保守配置，实际仍受服务器微信版本限制。原文件直接发送或单独压缩后仍超限时，明确提示微信上传大小限制、文件大小和当前上限；失败回复列出能确认的本地下载完整路径和所在目录。每次最多提交三个附件，剩余 ZIP 按聊天及请求人记录十五分钟，明确请求继续后才发送下一批。打包只读取原文件，使用独立发送快照，不移动、覆盖或删除原文件；每个 ZIP 校验 CRC。`file_send_enabled=false` 可关闭文件发送。每份文件分别记录发送状态，重试时跳过已确认发送的文件，结果不明时等待消息库确认。

发送暂存文件默认每两天清理一次，仅删除已保留满两天的 `outgoing_files` 下生成的 ZIP 和发送副本。`file_send_cleanup_days` 可设为 1～365 天，0 关闭；前端“微信与 Codex 设置”的“发送暂存文件清理间隔”可直接修改，保存后重启监听。监听运行时执行定时清理，即使关闭 Codex 回复或微信发送也会执行；监听停止时暂停，恢复后补检查。清理计划持久保存；待发送、待续发和结果不明的任务暂存文件保留，源下载文件、聊天及发送记录不删除。首次更新启动会检查已有过期文件，目录联接或符号链接不会被递归清理。

2026-10-30 已在本机微信文件传输助手实际发送普通测试附件和 Codex 聊天确认测试附件，各一份。第二项使用真实 CodexRunner 和模型：先查找且不发送，保存唯一候选，再确认发送，由真实 Listener、DesktopSpool、LocalDatabaseDriver、UIA 提交；消息库核实两份文件均有上传元数据且各只有一条记录，确认发送的队列提交次数为 1。自聊测试将已在真实微信消息库确认的测试文字作为隔离库的 incoming 事件接入，不代表另一个账号的入站采集已验证。报告和最终截图见 `data/manual-tests/20261030-181806-attachments/`；执行脚本为 `scripts/verify_attachment_live.py`。实测修复当前微信使用输入框内附件卡片、而非独立发送确认窗口的兼容问题，以及共享后端子解释器未启用 UTF-8 导致中文安装路径读取错误的问题。相关回归测试 80 项通过。本机结果不替代服务器微信版本的现场验证。

发送沿用桌面互斥、输入保护、紧急停止与持久去重。已提交但未确认的发送不会自动重发；微信原生文件消息记录确认后才记为完成。文件 UI 采用文件剪贴板及确认窗口；具体微信版本的兼容性需在真实账号上显式授权联调，自动测试不发送真实微信文件。

已接入 FusionLive 本地台账。每次 Codex 任务都会刷新当前聊天获准的项目文件目录，仅登记 `active=1`、`status=done` 的当前下载文件。读取时再次检查版本、路径、大小及内容哈希。文件保留在同步工具中，不重复复制下载文件、不移动或删除原件。

在管理中心“微信与 Codex → 配置设置”中可设置共享连接方式和可访问目录，网页对话默认继承同一份配置。`codex_transport` 可设为 `auto`、`websocket` 或 `https`；`codex_auto_access_dirs` 默认 `true`，自动发现同级目录并在页面显示，关闭后使用手动编辑的 `codex_access_dirs`。相对路径以配置文件所在目录为基准，手动空列表不会重新自动授权。微信始终只读，目录配置不会修改 Windows ACL；Windows elevated 仍保留底层基础读取权限，模型按目录列表控制工作范围。保存后重启微信监听生效。

聊天未指定独立来源时，自动从共享目录内发现同步工具台账，无需再填写 `sync_sources`。需要限定台账快照的项目时，可配置独立来源并给聊天选择同名 `sync_sources`（来源根目录仍须处于共享可访问目录内）：

```json
{
  "sync_sources": [
    {"id": "fusion", "root": "../FusionLive同步工具", "projects": ["17580"]}
  ],
  "chats": [
    {"id": "my_group", "name": "群的准确名称", "kind": "group", "username": "123456@chatroom",
     "reply": true, "sync_sources": ["fusion"]}
  ]
}
```

将这些字段合并到现有配置，按实际项目和聊天修改。独立来源限制助手快照中的项目，不取消共享目录内的直接只读查询权限；缩小实际任务目录范围应编辑 `codex_access_dirs`。`root` 相对于配置文件，须保留同步工具的 `downloads/`、`runtime/ledger.sqlite3` 和 `runtime/file_analysis/` 目录。仅复制台账而未复制实体文件时，目录会标记文件不可用。

Codex 可按文件名、项目或路径检索；分页读取文本、PCF、IDF及ZIP内文本；查询当前任务提交的管线、焊口与汇总结果。ZIP只读取指定成员，不落盘解压。PDF、Office、SHA或其他二进制文件可登记检索，尚未提取正文；解析结果查询也不能代替缺失的内容解析。各任务结果可能有重叠，不应直接相加当作项目总量。该接口是只读文件管理，不提供删除、移动、上传或修改原件。

## 整条流程的本地模拟

```powershell
..\.venv-analysis\Scripts\python.exe scripts/simulate_sync_pipeline.py
```

模拟使用相邻 `.venv-analysis` 运行同步工具，可通过 `--sync-python` 指定其Python；使用 `--output` 指定新的验证目录。真实下载函数接收模拟HTTP响应，完成临时文件落盘、大小/哈希校验和台账提交，再运行真实解压、PCF解析和简报生成。随后模拟群消息通过真实监听器、持久队列、CodexRunner以及模拟Codex子进程，执行文件检索、ZIP内PCF读取、缓存结果查询和材料等级读取，最终生成回复预览。检查重复事件只产生一个任务，以及源文件和数据库内容哈希未变。

结果保存在 `data/simulations/<时间>/simulation_result.json`、`reply_preview.txt` 和聊天工作目录的 `simulation_tools.json`。测试样本应得到1条管线、3个焊口（预制2、安装1）。不登录下载平台、不实际调用模型、不采集真实微信、不发送消息。真实Codex模型和微信UI链路仍需另外联调；这次模拟未修改现有账号及发送配置。

工作目录快照按聊天隔离，账号变化要求使用新状态目录。Codex 只读模式防止修改文件，不是阻止它读取同一 Windows 用户其他文件的完整权限隔离；Skill 明确禁止跨聊天和读取凭据。若要对不可信群聊开放，需要后续以受限工具或独立运行用户加强执行边界。

## 任务、回执和用量

- 本地采集持续运行，Codex 在单个后台工作线程中串行执行，生成时采集不会因等待模型而暂停。
- 任务、最终回复、用量字段和 UI 发送回执持久化。重复事件不会重复调用或发送。
- 确认未提交发送动作的最终回复及排队、开始、查询提示都会自动重试，默认最多尝试 3 次（含首次），间隔至少 5 秒；可通过 `send_max_attempts`、`send_retry_seconds` 调整。重试使用原有消息，不重新调用 Codex；提示正文、回复对象、次数及时间持久化，重启后仍有效。阶段已变化时跳过过时提示，例如开始后不再补发“正在排队”、生成完成后不再补发“正在思考/查询”。提示失败不阻止最终回复发送。
- 发送结果不确定或发送过程中进程中断时，会核对本地聊天记录；查到发送记录则确认成功，未查到时保留不确定状态，不盲目重发。超过消息有效期后停止处理。
- 超时、失败或进程中断的生成不自动重试。总生成时限 `codex_timeout_seconds` 默认 600 秒，回复有效期 `reply_max_age_seconds` 默认 900 秒。无进度时限 `codex_idle_timeout_seconds` 默认 300 秒（0 关闭）；持续有 JSON 进度时刷新，工具执行期间暂停无进度判断，总时限始终有效。任务错误区分本地配置读取、总生成时限、无进度和阶段未知的超时；旧版只有 `TimeoutError` 的记录无法区分原因。
- `query_progress_enabled` 默认开启：实时消费 Codex JSON 事件，在第一次工具执行开始时发送“正在查询……”。每条任务最多提示一次，任务已完成时跳过迟到提示；预览模式不发送。不向微信转发命令、文件路径、工具输出或思考内容。
- `mention_reply_sender` 默认开启：群聊排队、开始提示及最终回复按原消息的发送者账号选择微信原生 @ 成员，插入“回复对象：@成员”这一行，不在消息开头重复 @；私聊和查询提示不执行原生 @。成员名称从群成员信息读取，可用会话的 `sender_aliases` 映射账号到微信选择器中的显示名称。同名、成员不可用或原生选择器无法识别时保留为未发送，不用普通文本 @ 冒充提醒。2026-10-28 已在本机“RPA测试群”实测三条消息原生 @智能机器人；兼容输入框将 @ 暴露为 U+FFFC 嵌入对象，以及消息气泡在 @ 前插入分隔空格的行为。
- 原生 @ 候选弹出后，名称检索使用当前微信焦点输入，不再通过聊天输入框重新抢焦点；核对焦点进程和当前会话后才操作。发送前核对目标会话并清空其中已有草稿，包括旧版遗留草稿和人工输入，避免草稿阻碍后续任务；当前任务已核对一致的完整待发正文直接复用。会话变化或草稿未清空时不提交发送，等待后续重试。发送前错误记录具体阶段、异常类型及系统提供的 API/数字错误码，避免仅留下 `error`。
- 接收时超过 `reply_max_age_seconds` 的旧消息不入队；已入队任务的排队等待不计入有效期，包括重启后的等待。真正开始处理时记录 `started_at`，从此计算生成、发送等待和重试的有效期。`codex_timeout_seconds` 仍限制单次模型生成耗时，`max_reply_chars` 限制模型回答正文长度。
- 群任务进入等待队列时发送任务编号、回复对象、当时的排队序号及“正在排队中……”；排队序号不包含当前正在处理的任务，不持续刷新。实际开始时发送同一编号、回复对象、北京时间及“正在思考中……”，查询提示使用“任务编号：…\n正在查询……”。正式回复以任务编号、回复对象、结束时间及“回答如下：”开头。新任务编号使用持久化递增数字（1、2、3……），重复采集不重复分配，重启继续计数；旧任务保留原编号以保持发送去重。时间持久化，发送重试不改变消息正文，摘要仍只保存回答内容。提示受发送开关控制，原生@受“@回复人”开关控制。
- 模型在开始提示之前提交执行，提示失败不阻止生成。微信发送后只立即检查一次数据库，未确认时由后续轮询核实，避免每条消息额外同步等待 8 秒；结果不确定时不会重新点击发送。界面自动化仍顺序执行，会占用当前轮询数秒。草稿清理仅作用于已核对的当前发送目标，不清理其他会话。
- Codex 回复、推送文和简报图片共用 Windows 当前登录会话的命名互斥锁 `Local\ProjectTools.WeChatDesktop.v1`，从切换会话到恢复剪贴板完整串行执行；原有监听进程锁和简报去重台账继续保留。每条消息分别持锁，因此日报文字和图片之间可穿插已排队的 Codex 回复，但不会并发改动微信窗口或剪贴板。两套发送器都需更新并重启，旧进程不会自动使用新锁。
- 实际发送期间显示屏幕顶部操作提示，统一使用低级键鼠钩子拦截人工输入、允许自动化模拟输入，确保管理员与非管理员模式都能识别紧急快捷键。其他不遵循共享锁的软件仍须停止操作微信。模型生成和等待互斥锁期间不禁用输入。发送在独立进程执行，看门狗在 35 秒内结束卡住的进程，恢复输入并释放锁；保护初始化失败则不操作微信。
- 紧急快捷键为 **Ctrl + Shift + F12**（左右 Ctrl/Shift 均可），保护期间按下后立即终止当前桌面发送进程并恢复键鼠，同时持久暂停当前 Windows 用户的 Codex、推送文和简报发送，避免自动重试立刻再次禁用输入。双击项目根目录或同步工具目录的 `恢复微信发送.cmd` 手动恢复，也可运行 `python wechat_local/desktop_guard.py --resume`；`--status` 查看状态。暂停期间不消耗后续提示/回复及定时推送的重试预算；任务有效期与定时窗口仍照常计算。不确定的发送结果仍核实历史，不直接重发。
- 本机文件传输助手测试：`..\.venv-analysis\Scripts\python.exe scripts/verify_file_transfer.py --send`。仅向文件传输助手发送三条明确标记的测试消息并记录气泡观察结果；不调用模型，不修改监听配置。报告位于 `data/manual-tests/<时间>/result.json`。此私聊只能验证文字 @ 位置和发送链路，不能验证群成员原生 @。
- 群聊原生 @ 测试：同一命令追加 `--target RPA测试群`，仅向该群发送三条测试消息并原生 @智能机器人。此次实测记录和截图保存在 `data/manual-tests/20261028-185135/`；三条气泡全部核实，单条发送及核查约 6.5 秒。
- 草稿与补发实测：`..\.venv-analysis\Scripts\python.exe scripts/verify_draft_retry.py --send`。仅在 RPA测试群各模拟一次排队/开始提示的发送前中断，留下测试草稿，重开持久化发送库后等待重试；每阶段只实际发送一条消息，原生 @智能机器人，不调用模型。
- 输入保护与并发实测：`..\.venv-analysis\Scripts\python.exe scripts/verify_desktop_guard.py --send`。先验证 2 秒看门狗恢复，再同时向 RPA测试群提交一条 @智能机器人测试回复，向文件传输助手提交测试推送文及测试图片；记录两个发送器的持锁区间和屏幕提示截图，不发送业务日报。
- 快捷键实测：`..\.venv-analysis\Scripts\python.exe scripts/verify_emergency_hotkey.py` 在真实输入保护期间注入组合键，验证立即退出、持久暂停、桌面锁释放和恢复接口，不发送微信。自行演示可运行 `python wechat_local/desktop_guard.py --demo` 后手动按 Ctrl+Shift+F12，再运行恢复发送入口。
- `--jobs` 查看最近任务的状态、错误类型和 Codex 返回的 usage。完整回复保存在本地任务库；当前不把代理中间日志发送到微信。
- 目前只记录用量，尚未实现可强制中断的 Token/账户额度上限；耗时和回复长度不等于模型 Token 硬上限。
- 默认使用常驻 Codex App Server 进程，每群或私聊各自复用一个会话，达到上下文比例后轮换；长期记忆来自本地存档与按群摘要。兼容模式可切回独立 `codex exec`。

## 常驻后端与连接配置缓存

微信和管理中心网页共用 `wechat_local/shared_backend.py` 的本机后端代理。相同启动命令、启动目录、目录权限及配置/登录文件版本复用一个 Codex App Server 进程；不兼容配置分别隔离。网页每轮仍有自己的会话 ID、权限与消息流，微信仍按群/私聊隔离，代理按线程归属路由事件，拒绝跨入口操作会话及微信请求编辑权限。Windows 使用带认证的本机命名管道，不开放网络端口；注册信息与随机 IPC 认证材料在 `data/shared-codex/`，不进入更新包。

同一个共享后端最多同时生成 2 个任务，每个入口连接最多执行 1 个任务、保留 64 个已加载会话；请求及事件队列有界，超限明确返回错误，不隐藏排队后自动启动任务。全部入口连续空闲 120 秒后回收后端进程；最后一个入口释放连接时立即退出。停止微信只释放微信连接，不关闭网页仍在使用的后端。网页保留持久化恢复、归档等策略，归档/删除时取消后台订阅、保留历史，不增加预建或上下文轮换。微信继续使用自己的预建/轮换和摘要衔接。模型异常及超时不会自动重放本轮任务。

`codex_backend` 默认 `app-server`。首次任务启动 stdio 后端并初始化，后续任务复用同一进程；每群/私聊各自创建一个 `ephemeral=true` 会话并连续调用 `turn/start`，保持只读权限和禁止交互审批。默认在报告的上下文占用达到 55% 时后台预建一个空会话，达到 70% 时先完成当前回复，下一条问题切换到已预建会话；预建不发送用户问题、不启动额外的模型生成。可在管理中心或配置文件调整比例：`codex_session_rotate_percent`（1—99，默认 70）、`codex_session_prewarm`（默认 true）、`codex_session_prewarm_percent`（默认 55，开启时须小于轮换比例）。

比例采用 Codex `thread/tokenUsage/updated` 中最近一次 `last.totalTokens` 与 `modelContextWindow` 的估计值，不使用累计计费 `total`。`codex_context_window_tokens=0` 默认采用报告窗口；供应商不报告时可按实际模型手动填写，此值仅用于轮换判断，不会改变模型窗口。缺少用量或窗口数据时不编造百分比，改用 `codex_session_unknown_max_turns`（默认 20 轮）作为保守轮换上限。比例按实际收到的报告判断，单轮较长任务可能跨过阈值；不会因此中断当前回复，Codex 在单轮内自行压缩时也不会取消已标记的轮换。

续聊只发送新的问题、当前项目快照，以及尚未带入会话的近期消息/相关摘要；固定指引作为会话开发者指令提供。首次创建和轮换时补充当前会话最多 8 条、5000 字符以内的已确认问答摘要，衔接历史，不读取其他群的数据。预建空会话不会提前固化问题或摘要，因此切换时使用的是最新记忆。先前模型输出只是草稿，是否已发送以群聊观测和确认记忆为依据。

微信模型会话只在当前后端进程生命周期内保留；空闲回收、重启、配置/登录变更或异常后会重建，并用本地群聊记录与摘要衔接。旧会话异步取消订阅；累计 32 个退役会话或清理异常时在下一条任务前释放微信入口连接并重建其会话，不强杀网页仍在使用的共享进程。安全停止监听时释放微信连接及预建工作线程。现有查询进度提示、MD 摘要、结构化回复、总时限与无进度时限继续适用。

指定 HTTPS/WebSocket 时，通过同一常驻进程读取有效连接配置，按会话工作目录缓存，最多 60 秒。已知配置层或登录文件的路径/修改时间/大小变化会触发刷新；全局配置、命令或目录授权变化会在下次任务前重建后端。缓存仅在内存，失败结果不缓存，后端重建时清空；不记录配置原文或凭据到指标文件。

后端断开、协议请求超时或生成失败时，当前任务记为失败，不自动重放；下一条任务重新连接共享后端，必要时启动新进程。交互审批请求一律拒绝，只接收当前任务已完成的最终答复，不转发推理、工具原文或其他会话事件。兼容旧 CLI 或自定义包装器时，可在管理中心将“微信 Codex 后端”改为 `exec`；此兼容路径仍独立执行，不复用 App Server，程序不会在任务失败后自动切换模式再次生成。`generation-metrics.json` 的 `shared_backend_pid` 与网页 connected 事件中的共享 PID 可用于核实进程复用。

`generation-metrics.json` 记录后端/会话复用、预建是否完成/被使用、轮换原因、上下文占用及来源、会话创建耗时 `session_create_seconds`、请求实际等待会话的耗时 `session_acquire_seconds`。`turn_input_chars` 和 `*_sent` 记录本轮实际带入的文本/条数，`prompt_chars` 仍是程序准备的完整文本大小。`generation_seconds` 包含后端准备与生成，后端准备时间另列 `backend_setup_seconds`。空会话创建耗时与模型首轮连接、查询耗时是不同部分，预建不能保证消除全部延迟。当前仍完整刷新授权文件快照；增量文件目录刷新尚未实现。

## 群聊摘要与延迟优化

`chat_memory_enabled` 默认开启（私聊也按会话隔离）。同一次 Codex 调用用 JSON schema 返回 `reply` 和最多 300 字的 `memory_note`；只有 `reply` 会发送微信，不为总结追加模型调用。确认已发送后才将问题、发送者账号、原回复、短摘要和时间写入本地 `qa_memory`。预览、未发送、不确定及失败任务不会作为已告知内容写入记忆；旧版已确认发送的任务可自动导入“原回复摘录”。

每个会话工作目录 `data/chats/<账号与会话哈希>/memory.md` 展示最近 8 条有内容的摘要，原问答长期保存在数据库。下一次从该会话最近 500 条摘要中本地检索，最多提供 3 条相关问答，序列化字符预算为 2400；续聊会排除已带入的摘要，新会话另提供有预算限制的交接摘要。不整份读取 MD，不跨群检索。当前数量、状态及文件版本必须核对当前来源，历史摘要只用于理解追问、术语、人员及证据位置。关闭记忆后停止新摘要生成和自动带入，保留已有文件与数据库记录；当前模型会话仍可正常续聊。

默认近期消息减少到 6 条，排除机器人“正在思考”“正在查询”提示；`reply_target_chars` 默认 600，详细问题可展开，硬长度上限仍由 `max_reply_chars` 控制。每次构建当前授权快照后，程序直接汇总完整台账并随问题提供 `current_project_summary`，对应统计可直接回答；正文、焊口等仍按需查证，不复用陈旧统计。

会话工作目录的 `generation-metrics.json` 记录最近一次成功生成的准备耗时、生成耗时、工具调用次数、上下文字符数、记忆条数及模型返回的输入/输出用量，便于比较真实服务器上的延迟。未额外调用真实模型验证提速比例；单次生成短摘要也会增加少量输出，应以实测耗时及工具往返次数评估收益。

实现参考 [OpenAI Docs 延迟优化](https://developers.openai.com/api/docs/guides/latency-optimization) 的减少请求、过滤上下文、缩短非必要输出原则。已有服务器配置会保留；请在管理中心启用“群聊摘要与问答记忆”，按需将最近消息设为 6，保存并重启监听。

命令：

```powershell
..\.venv-analysis\Scripts\python.exe -m wechat_local --check
..\.venv-analysis\Scripts\python.exe -m wechat_local --once
..\.venv-analysis\Scripts\python.exe -m wechat_local --jobs
```

`--once` 仍会按配置决定是否生成和发送；检查环境请使用 `--check`。首次监听的历史基线不触发回复。
